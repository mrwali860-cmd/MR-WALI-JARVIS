# MR WALI JARVIS — LIVE OPERATOR CONSOLE V1

## Status
LOCKED CONTRACT — V1

## Mission
Turn the existing MR WALI JARVIS Business OS into a live operator console where Mr Wali can communicate with JARVIS by text or voice, assign work, receive clarification questions, approve gated actions, and observe real execution through the existing Core/Orchestrator/Execution Trace architecture.

## Non-Negotiable Principles
- Revenue over vanity.
- Execution over theory.
- Existing Core remains authoritative for business state and execution.
- Dashboard/Console is an operator surface, not a second business engine.
- No fake task progress or fake execution trace in production paths.
- Existing action boundary remains the only dashboard-originated mutation boundary.
- Preserve existing frozen components unless a contract explicitly requires a change.

## UX Contract
### Platforms
- Responsive browser: desktop and mobile.
- Desktop application may wrap the same web console later; no duplicate business logic.

### Communication
- Text input and chat history.
- Voice input.
- Voice output.
- JARVIS may ask clarification questions before execution.
- JARVIS may request explicit approval for gated actions.

### Core Visual
- The supplied JARVIS artwork is the visual reference and must not be redesigned.
- Original artwork remains the central identity element.
- Surrounding orbital/ring motion is animated without replacing the artwork.
- Central star has a restrained glow/pulse effect.
- Animation must remain professional and readable, not distracting.

### Main Screen Regions
1. Header: MR WALI JARVIS identity, navigation, connectivity/user status.
2. Left operator panel: JARVIS chat, text/voice controls, conversation history.
3. Center core: supplied artwork, online/execution state, current task.
4. Right live-task panel: active/pending/completed tasks from real state.
5. Right execution-trace panel: real execution events correlated by request_id.
6. Approval panel: visible only when approval is required; approval delegates through the existing action boundary.
7. System status: Orchestrator, services, database, APIs, uptime/health where available.

## Task Interaction Contract
Input example:
"JARVIS, find 20 Dubai real-estate leads."

Expected lifecycle:
1. Receive request.
2. Interpret request.
3. Ask clarification if required.
4. Produce/confirm plan when appropriate.
5. Delegate execution to existing Core/Orchestrator.
6. Stream or poll authoritative task/execution state.
7. Show request_id-correlated trace.
8. If approval is required, stop at the approval boundary and ask Mr Wali.
9. On approval, call the existing action boundary; do not mutate state directly from UI.
10. Show final result and completion state.

## State Contract
Supported operator-visible states include:
- ONLINE
- THINKING
- PLANNING
- EXECUTING
- WAITING_FOR_APPROVAL
- BLOCKED
- FAILED
- COMPLETED

The UI must derive these states from authoritative backend responses/events where available.

## Safety / Approval Contract
- Irreversible or policy-gated actions require explicit approval.
- Approval controls must identify the action being approved.
- UI approval delegates to the existing dashboard action boundary.
- UI must never bypass risk/approval policy or call providers directly.

## Services
The console must accommodate the existing service architecture and at minimum provide a clean surface for:
- Real Estate / Lead Generation
- E-commerce
- Trading
- AI Automation
- Additional services/adapters as they become available through the Service Catalog.

## Execution Trace Contract
Every meaningful execution path must remain traceable by request_id where the Core already supports it. The console may render trace data but must not become the persistence source for execution history.

## Voice Contract
- Voice input converts speech to a command/message for the same JARVIS command path used by text.
- Voice output reads JARVIS responses generated by the same backend interaction path.
- Voice is an interface layer, not a separate agent.

## Responsive Contract
- Desktop: full three-region command-center layout.
- Mobile: panels collapse/reorder without removing core task, chat, approval, or status functionality.
- No horizontal overflow for normal viewport sizes.

## Visual Quality Contract
- Dark professional command-center aesthetic.
- Central artwork remains dominant.
- Animations are smooth and subtle.
- Text must remain readable over animation.
- Loading/error/empty states must be intentional, not blank screens.
- Missing artwork must have a safe fallback rather than breaking the console.

## Acceptance Criteria
- [ ] Browser opens a working JARVIS operator console.
- [ ] Mobile layout remains usable.
- [ ] Text message reaches the real JARVIS backend path.
- [ ] Voice input uses the same command path.
- [ ] Voice output reads JARVIS responses.
- [ ] JARVIS can ask a clarification question.
- [ ] Real task state is visible.
- [ ] Execution Trace is visible and request_id-correlated where available.
- [ ] Approval-required actions stop and display an approval request.
- [ ] Approval uses the existing dashboard action boundary.
- [ ] Dashboard does not become a persistence/business-logic source.
- [ ] Central supplied artwork is preserved; orbital animation and star glow are layered around/over it without redesigning it.
